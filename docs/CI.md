# CI — فحص موقع الدلة موبايل

المشروع الحالي صفحة HTML ثابتة مع CSS مضمّن؛ لا يحتاج npm أو مرحلة build.

## ما ينفذه CI

- يعمل على Pull Requests إلى main، وبعد تحديث main، ويدعم التشغيل اليدوي.
- يشغّل فحوص الأمن والاختبارات بالتوازي، ثم يستخدم `validate` كفحص تجميعي مطلوب في قاعدة `Protect main`؛ يفشل إذا أخفق أي منهما.
- يتحقق من استخدام Python 3.10 أو أحدث، ويجمع ملفات `scripts/` و`tests/` لاكتشاف أخطاء الصياغة.
- يرفض استمرار فحص unittest إذا لم يكتشف أي حالات اختبار.
- يفحص HTML5 doctype وعناصر html/head/body/title/main/h1، والعنوان غير الفارغ.
- يتأكد من اللغة العربية واتجاه RTL وUTF-8 وviewport المتجاوب.
- يرفض IDs المكررة ومراجع aria-labelledby المفقودة وعلامات تعارض الدمج.
- يشغّل خادمًا محليًا مؤقتًا ويتحقق من HTTP 200 ونوع HTML وتطابق المحتوى في / و/index.html.
- يشغّل اختبارات حواجز التحقق، وحالات الحوادث والتعافي، وعقد التحقيق والثقة.
- يشغّل Bandit على سكربتات Python وGitleaks على تغييرات المستودع، كما كان قائمًا.
- ينشئ معاينة HTML قابلة للتنزيل على Pull Requests بعد نجاح فحوص الموقع؛ تُحتفظ بها 7 أيام ولا تنشر إلى الإنتاج. ظهور المعاينة لا يعني نجاح بوابات الأمن.

## بوابات DevSecOps

- CodeQL يحلل Python وJavaScript/TypeScript، ويرفع SARIF إلى Code Scanning عند توافر صلاحية الرفع. يفشل CI عند finding بدرجة أمنية 7.0 أو أعلى؛ في PRs القادمة من fork يجري التحليل محليًا دون رفع SARIF.
- Dependency Review يفشل طلب الدمج عند إضافة اعتماد معروف بثغرة High أو Critical.
- Trivy يفحص إعدادات IaC وDockerfile، ثم يفحص صورة Docker المبنية من commit نفسه؛ يفشل عند وجود مشكلة High أو Critical.
- Syft ينشئ SBOM بصيغة SPDX JSON من الصورة المفحوصة. يحفظ CI الصورة نفسها وملف SHA-256 وSBOM كـ artifact لمدة 7 أيام.
- `validate` لا ينجح إلا بعد نجاح الفحوص الوظيفية والأمنية. نشر ECS ينتظر نجاح CI على push إلى `main`، ويتحقق من أن commit ما زال رأس الفرع، ثم ينشر artifact نفسه بعد التحقق من SHA-256.

هذه الفحوص لا تستبدل مراجعة التنبيهات أو تدقيق إعدادات AWS. لا تُشغّل فحوص Dependency Review عند push إلى `main` لأنها تفحص تغييرات الاعتماد في Pull Request. عند إضافة صفحات أو JavaScript أو عملية build يجب توسيع الفحوص الوظيفية.

## التشغيل محليًا

من جذر المستودع، باستخدام Python 3.10 أو أحدث:

```sh
python3 -m unittest discover -s tests -v
python3 scripts/check_site.py
```

على Windows يمكن استبدال `python3` بـ `py -3`.

## التحقق والتفعيل

1. افتح PR الخاص بهذا التغيير وافحص تبويب Checks؛ يجب أن ينجح `validate`.
2. الاختبارات المرفقة تتحقق آليًا من رفض صفحات معطوبة دون تغيير صفحة الموقع.
3. لاختبار الحماية يدويًا: في فرع تجريبي وPR منفصل، احذف doctype من index.html؛ يجب أن يفشل validate ويمنع الدمج. أعد السطر وتحقق من نجاح التشغيل الجديد. لا تدمج نسخة الاختبار المعطوبة.
4. ادمج PR التحسين بعد مراجعته؛ يعمل الفحص تلقائيًا على main. بعد الدمج يتاح Actions → CI → Run workflow.
5. لا تغيّر اسم validate ولا تضف مرشحات paths تتخطى الفحص المطلوب.

لا يحتاج مسار الفحص إلى PAT أو مفتاح AWS ثابت؛ يستخدم `GITHUB_TOKEN` بصلاحيات محدودة، وتُحصر `security-events: write` في job الأمن. يلزم السماح بـ GitHub Actions وGitHub-hosted runners واتصالها لتنزيل قواعد الفحص.

لمنع الدمج عند فشل الأمن، أبقِ `validate` هو الفحص المطلوب في حماية `main`. فعّل أيضًا موافقة PR واحدة على الأقل، وراجع required reviewers لبيئة `production` قبل ضبط `ECS_DEPLOY_ENABLED=true`. تذكر آخر مراجعة موثقة في هذا المستند أن موافقات PR لم تكن إلزامية؛ أعد التحقق من الإعدادات الحالية في GitHub.
