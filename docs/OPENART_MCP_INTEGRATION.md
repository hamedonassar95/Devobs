# Devobs AI Intelligence × OpenArt MCP — governed media handoff

**Status:** opt-in integration contract; **not a running service**, not an OpenArt API client, not a production SaaS connector. This does not change AI-9/P01 gates.

## Supported integration boundaries

The [OpenArt MCP documentation](https://openart.ai/mcp/) provides a remote Streamable HTTP MCP endpoint: `https://mcp.openart.ai/mcp`, authenticated with user OAuth. The OpenArt [public Help Center](https://openart.ai/help/) states a traditional public API is not available. The [Codex MCP documentation](https://learn.chatgpt.com/docs/extend/mcp) documents Codex project/user MCP config and OAuth sign-in.

We implement a **human-controlled handoff**, not a fictitious REST client:

```text
Devobs operator / Codex authoring
  → local, private DRAFT manifest
  → Python offline schema/duplicate/size checks + SHA256 digest
  → manual security, brand, cost and privacy review
  → authenticated OpenArt MCP in ChatGPT/Codex (opt-in)
  → live model/mode selection and price quote
  → explicit owner approval for each specific credit charge
  → OpenArt generation in user's project
  → operator verifies image/video and records actual historyId / result URL in a reviewed PR
```

### Optional Codex MCP setup — never active by default

The repo's trusted `.codex/config.toml` is unchanged. Copy the *example* from `.codex/examples/openart-mcp.toml` into **your own** trusted user or project configuration only after reviewing the remote provider. Alternatively, in your own Codex CLI session use the documented command:

```shell
codex mcp add openart --url https://mcp.openart.ai/mcp
codex mcp login openart
codex mcp list
```

The OAuth sign-in must be completed by the account owner. The MCP connection is not proof of available credits, a generated asset, or an authorized charge. If your Codex environment does not expose these commands, use the installed `@OpenArt` plugin within ChatGPT instead. **Do not commit OAuth tokens, cookies or account identifiers.**

### Draft a creative request safely

```shell
python3 scripts/openart_media_request.py --input docs/examples/devobs_openart_brief.json
python3 -m unittest discover -s tests -p 'test_openart_media_request.py' -v
```

- JSON is required to have exactly `schema_version, job_id, project, state, visibility, deliverables`. `state=DRAFT` and `visibility=private` are mandatory.
- Up to three image/video deliverables, each with a unique ID, aspect ratio, language and descriptive prompt. Video duration (when requested) is a **preference**, not guaranteed compatibility; OpenArt live model form and live price must be checked.
- The CLI only validates input, emits a reproducible SHA256 fingerprint and **always** reports `approved=false`, `credits_authorized=false`, and `generation_submitted=false`.
- No external HTTP call, OpenArt model invocation, OAuth access, secrets, telemetry, SaaS activation, media generation or background process runs from this script.
- **This validation is not a content-privacy scanner.** The human operator must redact real CI logs, secrets, credentials, tenants, customer data, and internal URLs *before* sending any prompt or reference to an external provider.
- Before generating, ask the OpenArt plugin for current account credit balance, model/mode, exact configuration and estimated credit price; get **explicit owner consent** for that single request. A draft request's SHA is an audit identifier, not an approval signature.
- Do not auto-publish, link to public assets, or treat creative images as evidence of real Devobs production performance.

### Human review and receipts

When a user **separately authorizes generation** and it completes, record in a new reviewed change: request SHA, approved scope, chosen model/mode/settings, quoted and actual credits, OpenArt historyId/projectId (nonsecret metadata only), status and quality review, and content licensing check. Never fabricate media URLs or add assets unless successfully obtained. Never change `main` or release/AI-9 gates as a side effect.
