# إطار CBTA لتطوير كفاءات DevOps

## الغرض والنطاق

CBTA اختصار لـ Competency-Based Training and Assessment: تدريب وتقييم يثبت قدرة الشخص على أداء مهام محددة بأمان وبمستوى واضح، اعتمادًا على سلوك وأدلة قابلة للمراجعة. يربط هذا الإطار التعلم بمسارات Devobs الحالية مثل Pull Requests وCI والنشر والاستجابة للحوادث والرجوع.

هذا الإطار نسخة أولى لفريق يتعلم ويطوّر ممارساته. لا يمنح وحده صلاحية GitHub أو AWS، ولا يحل محل حماية الفروع أو المراجعة أو فحوص CI. التقييمات عملية ومحاكاة آمنة؛ لا تتطلب وصولًا إلى الإنتاج.

## مبادئ التقييم

- نقيس كل كفاءة على حدة؛ لا يخفي المتوسط ضعفًا في مجال حساس.
- النجاح يعتمد على تنفيذ يمكن ملاحظته ودليل مرتبط به، لا على حضور التدريب أو إجابة نظرية فقط.
- يستخدم المقيمون المعيار نفسه، ويسجلون ما شوهد وما لم يُختبر.
- يجوز التوقف وطلب المساعدة عند تجاوز النطاق أو ظهور خطر؛ التصعيد الصحيح جزء من الكفاءة.
- لا نطلب أسرارًا أو بيانات عملاء أو سجلات خام في سجل التقييم.
- لا ينفذ المتدرب تقييمًا على main أو الإنتاج، ولا يتجاوز فحصًا أو موافقة مطلوبة.
- يظل قرار منح صلاحيات التشغيل منفصلًا عن نتيجة التدريب ويخضع لضوابط المستودع والحساب.

## مستويات الأداء

| المستوى | الوصف القابل للملاحظة |
| --- | --- |
| L0 — معرفة | يشرح الغرض والمخاطر وحدود المهمة، ويحدد متى يجب التوقف. لا ينفذ تغييرًا تشغيليًا وحده. |
| L1 — تنفيذ بإشراف | يكمل مهمة محدودة باتباع الدليل وبوجود مشرف يراجع القرارات قبل التطبيق. |
| L2 — تنفيذ مستقل ضمن النطاق | ينفذ مهمة معتادة من دليل معتمد، يجمع الدليل، يتحقق من النتيجة، ويصعّد أي اختلاف دون تجاوز الضوابط. |
| L3 — مراجعة وتدريب | يراجع العمل بحثًا عن الحالات الحدية والمخاطر، يشرح سبب القرار، ويعطي ملاحظات قابلة للتطبيق أو يدرب عضوًا آخر. |

المستوى مرتبط بالكفاءة وسياق المهمة. حصول الشخص على L3 في CI لا يعني حصوله على L3 في AWS أو الاستجابة للحوادث.

## مجالات الكفاءة

1. **إدارة المصدر وPull Request:** إنشاء تغيير صغير واضح، وصفه، طلب المراجعة، والاستجابة للملاحظات مع الحفاظ على تاريخ Git.
2. **CI وجودة التغيير:** تفسير فحص validate، تمييز فشل المنتج عن فشل البيئة، وإصلاح السبب دون تعطيل الفحص.
3. **أمن الأتمتة وسلسلة التوريد:** فهم أقل الصلاحيات، حماية الأسرار، تثبيت الإجراءات، حدود OIDC، ومراجعة مصدر الأثر.
4. **Ansible والبنية كتعريف:** صياغة الحالة المطلوبة في Playbook، اختيار modules مناسبة، إدارة Inventory والمتغيرات، واختبار التكرارية بأمان.
5. **الإصدار والتحقق:** ربط الإصدار بـ commit أو artifact معروف، مراجعة شروط البيئة، والتحقق من صحة الخدمة بعد التغيير.
6. **المراقبة والاستجابة للحوادث:** جمع أقل دليل لازم، تصنيف المشكلة، اقتراح إجراء مناسب، وحفظ البيانات الحساسة خارج التقارير.
7. **الرجوع والتعلم التشغيلي:** اختيار baseline موثوق، الرجوع عبر المسار المحمي، التحقق من النتيجة، وتسجيل ما يمنع التكرار.

## دورة التقييم

1. يحدد المتدرب والمقيم الكفاءة والمستوى المستهدف وسيناريو آمنًا.
2. ينفذ المتدرب المهمة أو يشرح قرارًا مدعومًا بأدلة عند كون التنفيذ غير آمن.
3. يتحقق المقيم من السلوك والنتيجة وفق مصفوفة التقييم.
4. يسجل الطرفان روابط PR أو تشغيل CI أو ملف تمرين، دون أسرار أو بيانات حساسة.
5. تصنف النتيجة إلى: مجتاز، يحتاج تدريبًا إضافيًا، أو لم يُلاحظ بعد.
6. يحدد المقيم خطوة تدريب وتاريخ إعادة تقييم عند وجود فجوة.

لا يُعد التشغيل الناجح وحده دليلًا كافيًا إذا كان المتدرب لا يستطيع تفسير النتيجة أو تحديد مخاطرها.
