# توصية سعة الموارد القابلة لإعادة الاستخدام

## الوضع الحالي

يحتوي CI في Devobs بالفعل على اختيار الفحوص الملائمة للتغيير، وتقدير تفسيري لمخاطر النشر، واستعادة آلية محكومة لنسخة GitHub Pages الثابتة عند فشل فحص الصحة. أضفنا إجراء GitHub قابلًا لإعادة الاستخدام يحول مقاييس CPU والذاكرة الحديثة إلى توصية محدودة لعدد النسخ.

الإجراء **لا يغيّر بنية الإنتاج**. Devobs نفسه موقع Pages ثابت، لذلك لا يملك خدمة تشغيلية يمكن تحجيمها. تحصل المشاريع المستهلكة على التوصية بعد أن توفر مقاييس حقيقية، ثم تربط الناتج بمهايئ خاص بمنصة التشغيل لديها. هذا الحد يمنع صلاحيات cloud عامة أو كتابة غير مقصودة من مستودع مركزي.

## استخدام الإجراء

يجب أن يشغّل المستهلك خطوة checkout أولًا حتى يكون ملف المقاييس داخل مساحة عمل المستودع، ثم يستدعي الإجراء على SHA كامل وثابت من Devobs:

```yaml
steps:
  - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
    with:
      persist-credentials: false

  - name: Recommend workload capacity
    id: capacity
    uses: hamedonassar95/Devobs/.github/actions/capacity-recommendation@<DEVOBS_COMMIT_SHA>
    with:
      metrics_file: .automation/workload-metrics.json
      min_replicas: 1
      max_replicas: 12
      target_cpu_percent: 65
      target_memory_percent: 75

  - name: Show recommendation
    env:
      DECISION: ${{ steps.capacity.outputs.decision }}
      REPLICAS: ${{ steps.capacity.outputs.recommended_replicas }}
      REASON: ${{ steps.capacity.outputs.reason }}
    run: |
      echo "Decision: $DECISION"
      echo "Recommended replicas: $REPLICAS"
      echo "Reason: $REASON"
```

استبدل `<DEVOBS_COMMIT_SHA>` بمعرّف commit كامل من Devobs، ولا تترك placeholder في workflow حقيقي. لا تمنح هذه الخطوة صلاحية نشر أو تعديل موارد. يضيف المستهلك خطوة منفصلة خاصة بمزود الخدمة إذا احتاج تطبيق التوصية، مع صلاحيات أقل ما يمكن، شروط بيئة محمية، وموافقة بشرية عندما يكون التغيير مؤثرًا.

## عقد ملف المقاييس

ينبغي لمهايئ المنصة إنشاء JSON بهذا الشكل. كل عنصر في مصفوفتَي CPU والذاكرة قياس مئوي للحمل نفسه وفي اللحظة نفسها:

```json
{
  "schema_version": 1,
  "observed_at": "2026-10-16T12:00:00Z",
  "window_minutes": 60,
  "current_replicas": 4,
  "last_scaled_at": "2026-10-16T10:00:00Z",
  "cpu_utilization_percent": [48, 55, 61, 58, 63, 52],
  "memory_utilization_percent": [50, 54, 57, 60, 55, 53]
}
```

`last_scaled_at` مطلوب كي يوصي الإجراء بتخفيض العدد؛ غيابه يمنع التخفيض فقط. استخدم وقت القياس الأخير في `observed_at`، لا وقت تشغيل workflow. يجب تطبيع نسب CPU والذاكرة إلى السعة المحجوزة لكل نسخة وبطريقة ثابتة بين الملاحظات؛ لا تستخدم استهلاك الخدمة الإجمالي دون تطبيعه إلى عدد النسخ. لا تصلح هذه السياسة إلا لحمل يمكن توزيعه أفقيًا. يرفض الإجراء ملفًا خارج مساحة عمل المشروع، وبيانات غير صالحة، وقياسات أقدم من الحد المحدد. لا تضع أسرارًا أو بيانات عملاء في الملف.

## سياسة التوصية الافتراضية

- يعتمد القرار على المئين 95 من القياسات، لا على متوسط قد يخفي قفزات الحمل.
- يوصي بالزيادة عندما يتجاوز أشدّ مؤشري CPU أو الذاكرة هدفه بأكثر من 5%. يحد الزيادة إلى 50% من العدد الحالي في التشغيل الواحد (نسخة واحدة على الأقل عند تعذر تمثيل النسبة بوحدات صحيحة)، ولا يتجاوز `max_replicas`.
- يوصي بتخفيض **نسخة واحدة فقط** عندما يكون المئين 95 لكلا المؤشرين عند نصف الهدف أو أقل، ويكون حد البيانات حديثًا، وتكون فترة التهدئة منذ آخر تغيير قد انتهت. لا ينزل عن `min_replicas`.
- يلزم وجود ست ملاحظات متزامنة على الأقل افتراضيًا. عند قدم المقاييس أو نقصها تكون النتيجة `hold`.
- يلزم أن تغطي نافذة الملاحظات 30 دقيقة على الأقل قبل أي تخفيض، إضافة إلى شرط التهدئة.
- النتيجة حتمية وسهلة التدقيق؛ لا يتصل الإجراء بخدمة AI خارجية ولا يطبّق أي تغيير.

هذه السياسة تخص **التحجيم الأفقي لعدد النسخ**. لا تستنتج أحجام CPU أو الذاكرة المناسبة، ولا تستبدل autoscaler أصليًا في Kubernetes أو Cloud Run أو ECS. يجب أن يوفّر كل مشروع مقاييس صحيحة ومهايئًا لمنصة تشغيله، وأن يحدد سقفًا يحترم الميزانية وحدود الخدمة. لا تشغّل تحديثات الموارد من أحداث Pull Request غير الموثوقة.

للتحجيم المستمر في الإنتاج، ابدأ بآلية المنصة الأصلية: [Kubernetes Horizontal Pod Autoscaler](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)، [Cloud Run instance autoscaling](https://cloud.google.com/run/docs/about-instance-autoscaling)، أو [ECS target tracking](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-autoscaling-targettracking.html). هذه الخدمات تراقب الحمل وتدير السعة على نحو متواصل؛ إجراء Devobs يلائم المشاريع التي تريد قرارًا قابلًا للتدقيق ضمن سير CI/CD أو قبل وصل المخرجات بمهايئها الخاص.

## ربط النتيجة بالتطبيق

يعرض الإجراء `decision` و`recommended_replicas` و`reason` كمخرجات GitHub Actions، ويضيف ملخصًا للتشغيل. يقرر المستهلك كيف يطبّق العدد بمنصة التشغيل التي يملكها. لا يوجد حاليًا تطبيق تلقائي لمزود محدد في Devobs لأن مركز الأتمتة لا يملك بيانات عبء عمل أو خدمة إنتاجية مشتركة، كما أن ربط كل منصة يتطلب حدودها وصلاحياتها واختبارات صحتها.

قبل تفعيل تطبيق آلي، أضف إلى المشروع المعني: مصدر قياس موثوق، حدودًا وموازنة، اعتماد OIDC أو هوية قصيرة العمر، بيئة GitHub محمية، تحققًا بعد التحجيم، ومسار تراجع خاصًا بالمزود. راجع [مركز الأتمتة](AUTOMATION_HUB.md) لاختيار المسار الأساسي للمشروع دون تشغيل مسارات مكررة.
