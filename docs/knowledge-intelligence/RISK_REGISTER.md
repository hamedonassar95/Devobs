# Risk register

**Scope:** Evidence-based design risks for future local-first Knowledge
Intelligence work. Ratings describe potential impact if the system were
implemented, not a claim that a production incident has occurred.

| ID | Severity | Risk and evidence | Existing protection | Required mitigation / owner |
| --- | --- | --- | --- | --- |
| KI-R1 | CRITICAL | Tenant leakage if retrieval omits a trusted tenant predicate. Current tenant gate is explicitly offline and excludes identity middleware. | Synthetic OfflineTenantGate tests and PostgreSQL RLS source contract. | Verify identity, forced RLS, service roles and cross-tenant query/update/delete tests on the exact local schema before any API connection. Owner: security/data. |
| KI-R2 | HIGH | Prompt injection or executable instructions in retrieved documents could be mistaken for system policy. Current sources include external repo/docs content. | Existing AI input boundaries mark incident text untrusted; no knowledge retriever exists. | Preserve trust labels, parser sandbox, never execute retrieved instructions, separate evidence from policy/tool authorization, and test injection fixtures. Owner: AI security. |
| KI-R3 | HIGH | Secrets or customer/private records could enter an index and persist in derived chunks, vectors, logs, caches or backups. | Existing redaction and secret scanning tools; memory is metadata-only and explicit data-source limits. | Source allowlist, secret scan plus manual review, data minimization, approved purpose/retention, no raw query/span telemetry, deletion propagation. Owner: privacy/data. |
| KI-R4 | HIGH | Current PostgreSQL and human-approval evidence may be mistaken for live readiness. PR #785 is newer than the committed ledger/STATE snapshot. | Local CI passed on base; ledger stale discrepancy is recorded. | Reconcile state/ledger in an appropriate reviewed change; verify live connectivity only under a separate approved scope. Do not infer from source configuration. Owner: repository governance. |
| KI-R5 | HIGH | The expiring Render Free PostgreSQL database could be used accidentally as a knowledge store, risking loss or violation of the owner decision. | Owner decision records natural expiry and prohibits modification, export, replacement, and cost. | Hard-exclude Render from all prototypes; use synthetic local-only fixtures. Do not run provider actions. Owner: release/data. |
| KI-R6 | HIGH | Unsupported production quality claims from synthetic or historical evaluation could close AI-9 incorrectly. | Evaluation docs distinguish synthetic fixtures; AI-9 is BLOCKED. | Freeze unbiased retrieval data, holdout, human labels, confidence bounds and independent review; never claim the target is met from synthetic coverage alone. Owner: evaluation. |
| KI-R7 | HIGH | Deletion and legal retention can diverge across source copies, vector indexes, caches and backups. | Incident-memory contract is in-process and documents retention/replay limits. | Define deletion SLA, retention classes, immutable tombstone, backup expiration, restore-time deletion replay and audit tests before durable data. Owner: data governance. |
| KI-R8 | HIGH | Resource exhaustion from unbounded parsing, chunking, indexing, model loading or high-cardinality telemetry. | Existing parsers and OTel paths use bounds; monitoring metrics are constrained. | Set explicit byte/chunk/CPU/RAM/time/concurrency/index limits, backpressure and cleanup; benchmark each full reindex/query path. Owner: reliability. |
| KI-R9 | MEDIUM | Version drift could make embeddings, tokenizer, chunking, parser or index results non-reproducible. | Existing lockfiles and source SHAs support reproducible CI inputs. | Pin dependency/model/artifact hashes and policy versions; store all versions in each index manifest and provide deterministic rebuild tests. Owner: ML platform. |
| KI-R10 | MEDIUM | A new vector store or experiment tracker could duplicate existing PostgreSQL, Graphify, local evaluation or OTel capabilities and increase operations. | Repository already contains source graph, relational contracts, synthetic evaluation and local observability. | Keep ports small; require evidence of a gap before adding a service; compare against current components and document rollback. Owner: architecture. |
| KI-R11 | MEDIUM | OSS software license may be confused with model-weight, plugin, support or hosted service terms. | Source register separates library licenses from service costs and marks reference access limits. | Review every model and plugin separately; do not download gated weights or activate paid service without review. Owner: legal/engineering. |
| KI-R12 | MEDIUM | Cost switches may be confused with hard account-level spending caps. | Existing AI workflow has explicit budget opt-in; it is not a dollar cap. | Keep paid providers disabled; require exact budget, usage telemetry, hard provider limits and independent owner approval before activation. Owner: finance/platform. |
| KI-R13 | MEDIUM | Stale citations may refer to changed or deleted source revisions. | Existing evidence contracts carry source SHA and event digests; memory filters by time and provenance. | Revalidate source version and offset at response time; return stale/blocked status instead of substituting content. Owner: retrieval. |
| KI-R14 | MEDIUM | Existing human review design could be bypassed by giving an agent direct write tools. | Deterministic policy denies unlisted actions; approved state has no transition. | Keep retrieval role read-only and model outputs proposal-only; action-bound approval remains independent from the agent. Owner: agent security. |

No mitigation in this register authorizes a cloud change, migration, paid
service, model call, production data import, or weakening of P01, AI-9, or Codex
runtime gates.
